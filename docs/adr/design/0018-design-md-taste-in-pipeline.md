# DESIGN.md 의 taste 레이어를 파이프라인 안에서 생성한다

Date: 2026-06-16

## Status

Accepted (2026-06-16)

## Context

design/0015 는 DESIGN.md 를 디자인 의도의 단일 소스로 도입하면서 세 영역을 정의했다 — 전역 디자인 시스템(수치값), 전역 톤 & 방향(산문), 페이지별 요청(산문). 이 중 **전역 디자인 시스템만 파이프라인이 LLM(머신 디자인 요약)으로 자동으로 채우고, 산문 두 영역은 빈 placeholder 주석으로 남긴다.** 의도는 사람이 그 자리를 직접 편집해 추상 의도를 불어넣는 것이었다.

그런데 실제 운영에서 이 산문 영역은 사실상 비어 있는 채로 생성이 진행된다. 호출하는 에이전트가 별도의 "프레젠테이션 디자인 taste" 지침(팔레트가 그라데이션 wash 가 되지 않게, 모든 슬라이드를 제목+불릿 3개로 찍어내지 않게, 아이콘 카드 트리오를 남발하지 않게, 덱 전체에 내러티브 아크를 두게 — 한마디로 "AI slop 회피")을 **선택적으로, 수동으로** DESIGN.md 에 적어 넣어야만 taste 가 반영된다. 이 지침을 외부 스킬 형태로 두면 다음 문제가 있다.

- **누락이 기본값이 된다.** 에이전트가 스킬을 호출하지 않으면 산문 영역이 빈 채로 생성돼, 슬라이드 본문 프롬프트에 taste 가 전혀 주입되지 않는다. 그 결과가 전형적인 AI 기본형 덱(균일한 카드 트리오, 무아크, 그라데이션 배경)이다.
- **단일 소스 원칙과 어긋난다.** design/0015 는 "디자인 의도를 한 곳에서, 생성 전에" 반영한다고 했는데, taste 가 파이프라인 바깥의 호출자 행동에 의존하면 그 의도가 도구 사용자(MCP 클라이언트)마다 들쭉날쭉해진다.
- **MCP 도구 단독으로는 재현 불가능하다.** 같은 outline 으로 도구를 호출해도, taste 스킬을 거쳤는지 여부에 따라 결과 품질이 갈린다. 도구의 출력 품질이 외부 컨텍스트에 좌우된다.

요컨대 taste 는 "사람이 원하면 채우는 선택 영역"이 아니라 **덱이 AI slop 으로 떨어지지 않기 위한 기본 바닥(floor)** 인데, 현재는 그 바닥을 파이프라인 밖에 두고 있다.

또한 관찰된 slop 의 상당 부분은 톤(팔레트·격식)이 아니라 **구조**에서 온다 — content 슬라이드가 전부 균일한 카드 트리오/쿼드로 찍혀 나오고, 덱 전체에 loud/breathe 의 리듬이 없다. 전역 톤 산문만 채워서는 이 구조적 균일성을 깨기 어렵다. 균일성을 깨는 가장 직접적인 수단은 design/0015 가 정의한 **페이지별 요청**(특정 슬라이드만 다른 아키타입으로 — 좌우 비교, 풀블리드 한 문장, 다이어그램 등)인데, 이 영역도 지금은 빈 placeholder 로 남아 사람이 수동으로 채워야만 동작한다. 즉 slop 을 깨는 가장 강한 지렛대가 파이프라인 밖 수동 영역에 방치돼 있다.

## Decision Drivers

- taste 가 MCP 도구 파이프라인 안에서 보장돼야 한다 — 외부 스킬 설치·호출 여부와 무관하게.
- design/0015 의 "디자인 의도는 DESIGN.md 단일 소스에, 생성 전에" 원칙을 깨지 않아야 한다. taste 는 DESIGN.md 를 우회해 프롬프트에 직접 박는 게 아니라 **DESIGN.md 의 산문 영역을 통해** 흐른다.
- 사람의 편집 우선권은 유지돼야 한다 — 자동 생성된 taste 를 사람이 덮어쓸 수 있어야 한다 (DESIGN.md 는 사람이 편집하는 문서다).
- taste 는 outline(주제·청중·시간·덱 구조)에 근거해 *이 덱에 맞게* 생성돼야 한다. 모든 덱에 같은 문구를 붙이는 정적 템플릿은 그 자체가 또 다른 slop 이다.
- slop 의 구조적 축(균일 카드 트리오, 무아크)을 실제로 깨야 한다 — 톤 산문만으로는 부족하고, 페이지별 deviation 까지 닿아야 한다.
- 단, deviation 은 선별적이어야 한다 — 모든 슬라이드를 건드리면 새로운 균일성이 되고 design/0015 의 "한 곳에서 관리" 원칙에 역행한다.
- 기존 프로젝트·이미 채워진 DESIGN.md 의 동작은 바뀌지 않아야 한다 (하위 호환).

## Decision

**DESIGN.md 초안 자동 생성 단계가 전역 디자인 시스템(수치값)뿐 아니라 전역 톤 & 방향(산문) 영역까지 outline 에 근거해 LLM 으로 채운다.** taste 지침은 외부 스킬이 아니라 이 초안 생성 프롬프트에 내장된다.

- 초안 생성 시, LLM 은 outline 의 주제·청중·발표 시간·슬라이드 구성을 읽고 "전역 톤 & 방향" 산문을 작성한다 — 청중과 발표 상황에 맞는 격식·밀도·대비, 덱의 내러티브 아크(어디서 열고, 어디서 전환하고, 어떻게 닫는지), 한 곳에 집중할 시그니처 요소. 동시에 AI slop 안티패턴(균일 제목+불릿, 아이콘 카드 트리오, 그라데이션 wash, 스톡 메타포, 무아크 균일 밀도)을 회피하도록 방향을 잡는다.
- 이 산문은 placeholder 주석을 **대체**해 DESIGN.md 에 기록된다. 그 다음은 design/0015 의 기존 흐름 그대로 — 사람이 열어 편집할 수 있고, 슬라이드 생성 시 전역 영역으로 모든 슬라이드 프롬프트에 주입된다.
- **페이지별 요청 영역도 초안 생성이 채운다 — 단, 선별적으로.** LLM 은 전역 톤을 정한 뒤, outline 의 슬라이드 구성을 보고 *기본 아키타입을 그대로 따르면 균일 slop 이 되는 슬라이드* 에 한해 페이지별 deviation 요청을 단다 (예: 병렬 항목이라 카드 트리오로 흐를 슬라이드를 좌우 비교나 다른 레이아웃으로, 핵심 전환점 슬라이드를 풀블리드 한 문장으로, 아크상 "breathe" 지점을 여백 위주로). 모든 슬라이드에 일괄로 요청을 달지 않는다 — deviation 이 모든 슬라이드에 붙으면 그 자체가 새로운 균일성이 되고, design/0015 가 경계한 "의도가 슬라이드마다 흩어지는" 상태가 된다. 시그니처를 한 곳에 집중하고 나머지는 조용히 두는 절제가 규칙이다.

### taste 지침을 어디에 두는가

taste 안티패턴·원칙은 슬라이드 본문 생성 프롬프트가 아니라 **DESIGN.md 초안 생성 프롬프트**(톤과 페이지별 deviation 을 함께 쓰는 단계)에 둔다. 이유: design/0015 가 정한 데이터 흐름(의도는 DESIGN.md 를 거쳐 슬라이드로 내려간다)을 우회하지 않기 위해서다. taste 를 본문 프롬프트에 직접 박으면 DESIGN.md 가 단일 소스라는 원칙이 깨지고, 사람이 의도를 편집해도 본문 프롬프트의 고정 taste 와 충돌한다. taste 를 초안 생성 단계에 두면, 생성된 산문(톤 + 선별된 페이지별 요청)이 곧 사람이 보고 고칠 수 있는 단일 소스가 된다.

### 외부 스킬과의 관계

동일 taste 를 담은 외부 스킬이 있더라도, 그것은 이제 파이프라인 기본 동작의 **상위 보강(사람이 더 깊은 디자인 의도를 직접 주입하고 싶을 때)** 일 뿐, taste 가 반영되기 위한 필수 경로가 아니다. 스킬을 전혀 호출하지 않아도 도구 단독으로 taste 바닥을 보장한다.

### 사람 편집·재생성과의 상호작용

DESIGN.md 가 이미 존재하면(사람이 편집했거나 이전에 생성됐으면) 초안 재생성을 건너뛰는 design/0015 의 동작을 유지한다 — 자동 taste 는 **초안이 처음 만들어질 때 한 번** 채워지고, 이후 사람의 편집이 우선한다. 사람이 톤을 비워서 다시 만들고 싶으면 DESIGN.md 를 지우고 재생성하는 기존 경로를 쓴다.

## Consequences

### Positive

- MCP 도구가 외부 스킬 없이도 taste 바닥을 보장한다 — 같은 outline 이면 호출 컨텍스트와 무관하게 일관된 품질이 나온다 (재현성).
- taste 가 DESIGN.md 산문으로 드러나, 사람이 읽고·고치고·diff 할 수 있다 (design/0015 단일 소스 원칙 유지·강화).
- 톤이 outline(주제·청중·시간)에 근거해 *이 덱에 맞게* 생성돼, 정적 템플릿식 slop 을 피한다.
- 선별적 페이지별 deviation 으로 구조적 slop(균일 카드 트리오·무아크)까지 깬다 — 톤만 채우는 안보다 실효가 크다.
- 슬라이드 본문 프롬프트는 손대지 않으므로, taste 와 본문 생성 규칙(폰트 하한·그리드 등)의 관심사가 분리된 채 유지된다.

### Negative / Risks

- DESIGN.md 초안 생성에 LLM 부담이 늘어난다 — 기존엔 수치값 요약만 생성했는데 산문 톤까지 생성하므로 토큰·지연이 증가한다 (초안 생성 1회 한정).
- 자동 생성된 톤·deviation 이 사람의 실제 의도와 어긋날 수 있다. design/0015 의 편집 우선권으로 완화되지만, 사람이 DESIGN.md 를 안 보고 넘기면 자동 생성분이 그대로 적용된다. 특히 잘못 부여된 페이지별 deviation 은 멀쩡한 슬라이드를 일부러 비틀 수 있어, 톤보다 오작동 비용이 크다.
- deviation 을 "어떤 슬라이드가 균일 slop 위험인가" 판단하는 것은 LLM 의 주관이라, 과소(아무 데도 안 닮) 또는 과다(너무 많이 비틈) 양극단으로 흐를 수 있다. "선별·절제"가 프롬프트 지침으로만 강제되므로 결과 편차가 톤 단독보다 크다.

### 검증으로 확인된 사항

- 초안 생성 응답은 준비 단계가 반환한 단일 스키마와 수신 단계의 동일한 모델로 엄격하게 검증한다. JSON fence 포함/미포함은 허용하지만, 불완전한 페이지 요청이나 잘못된 타입은 일부만 복구하지 않고 전체 응답을 거부한다.
- 기존 DESIGN.md 가 있으면 초안 재생성 LLM 호출(taste 생성 포함)을 건너뛴다 — 사람 편집 우선권이 보존됨을 확인.
- import 경로(outline 없음)는 taste 자동 생성 대상이 아니며, 추출 기반 요약 + 빈 placeholder 를 그대로 유지한다 (하위 호환).
- 생성된 톤·페이지별 요청은 design/0015 의 기존 주입 경로(전역 톤=모든 슬라이드, 페이지 요청=매칭 슬라이드)를 그대로 타므로, 슬라이드 본문 생성 프롬프트는 무변경이다.
- taste 지침이 프롬프트에 글로 박히는 만큼, 안티패턴 목록이 시간이 지나며 그 자체로 새로운 균일성(모든 덱이 같은 회피 전략을 따름)을 낳을 위험이 있다 — 지침은 회피 목록이 아니라 "이 덱에 맞는 선택"을 유도하는 방향으로 유지해야 한다.
- 외부 스킬과 파이프라인 내장 taste 가 동시에 존재하면 지침이 두 곳에 중복된다. 한쪽이 갱신될 때 다른 쪽이 드리프트할 수 있어, 파이프라인 내장본을 정본으로 삼아야 한다.
