# DESIGN.md 가 배경 이미지 자동 주입을 제어한다

Date: 2026-06-15

## Status

Accepted (2026-06-15)

## Context

타이틀·클로징 슬라이드는 export 시점에 테마별 기본 배경 이미지(그라데이션 PNG)가 자동으로 주입된다. 이 주입은 슬라이드 타입과 테마(다크/라이트)만 보고 무조건 일어난다. LLM 이 생성하는 디자인 스펙에는 배경 이미지가 들어 있지 않으며, 타이틀/클로징 생성 프롬프트는 오히려 "배경색을 비워라(배경 이미지가 자동 삽입된다)"라고 지시해 배경 결정을 LLM 바깥의 export 단계로 위임한다.

design/0015 로 DESIGN.md(사람이 편집하는 디자인 의도 단일 소스)를 도입한 뒤 이 동작이 문제로 드러났다. 사용자가 DESIGN.md 의 "톤 & 방향"에 "그라데이션·풀블리드 배경 이미지를 쓰지 말라"고 적어도, 그 의도는 슬라이드 생성 프롬프트에만 주입되고 **export 단계의 배경 주입 결정에는 도달하지 못한다**. 그 결과 콘텐츠 슬라이드는 톤을 충실히 따르는데 타이틀/클로징만 사람이 금지한 그라데이션 배경이 그대로 깔린다.

근본 원인은 두 가지가 충돌하는데 우선순위가 코드에 없다는 것이다.

- design/0010 의 기본 테마는 그라데이션 계열이고, 타이틀/클로징 자동 배경이 그 산출물이다 (단, 배경 이미지 자동 주입 자체를 결정한 ADR 은 없었다 — 문서화되지 않은 기본 동작).
- design/0015 는 DESIGN.md 가 디자인 의도의 단일 소스라고 선언했다.

배경 자동 주입은 design/0015 의 "DESIGN.md 가 정본" 원칙이 닿지 않는 사각지대에 있었다.

## Decision Drivers

- DESIGN.md 가 디자인 의도의 단일 소스라는 design/0015 원칙은 배경에도 적용돼야 한다.
- 배경 정책은 사람이 산문으로 흘려 쓴 의도가 아니라 결정론적으로 파싱돼야 한다 (design/0015 의 "전역 시스템은 결정론 파싱" 원칙).
- 기존 프로젝트·DESIGN.md 를 건드리지 않은 신규 프로젝트의 외형은 바뀌지 않아야 한다 (하위 호환).
- 사용자가 직접 지정한 배경(임포트 라운드트립 등)은 자동 주입보다 우선해야 한다.

## Decision

**DESIGN.md 의 전역 디자인 시스템에 배경 이미지 정책을 결정론적 키로 승격하고, export 경로가 이 값을 읽어 타이틀/클로징 자동 배경 주입 여부를 제어한다.**

- DESIGN.md "전역 디자인 시스템"에 배경 정책 항목을 둔다. 값은 자동 주입을 켜는 상태(기본 그라데이션)와 끄는 상태(단색 배경으로 마감) 중 하나다.
- 테마(다크/라이트)처럼 이 값이 머신 디자인 요약으로 파싱·직렬화되며, export 경로가 테마를 읽던 자리에서 이 값을 함께 읽어 배경 주입 게이트에 넘긴다. HTML·PPTX 두 export 경로 모두 동일하게 적용한다.
- 자동 주입을 끄면 타이틀/클로징도 콘텐츠 슬라이드처럼 단색 배경(DESIGN.md 배경색)으로 마감한다. 타이틀/클로징은 평소 배경 이미지가 깔리므로 생성 시 배경색을 비워두는데, 주입을 끈 경우엔 이미지 폴백이 없어 빈 배경이 된다. 이를 막기 위해, 디자인 스펙을 단일 소스로 유지하도록(design/0001) **생성 시점에 타이틀/클로징 배경색을 deck 배경색으로 결정론적으로 채운다** — 프롬프트의 비결정적 지시에 의존하지 않는다.

### 기존 명시 배경과의 우선순위

자동 주입은 가장 낮은 우선순위다. 슬라이드에 사용자가 명시한 배경(이미지 또는 단색)이 있으면 그것이 자동 주입을 덮어쓴다 — HTML 경로는 명시 배경 이미지를, PPTX 경로는 명시 배경 바이트를 이미 우선 적용하므로, 정책 키는 "명시 배경이 없을 때 자동 주입을 켤지"만 결정한다.

### design/0010 과의 관계

design/0010 의 그라데이션 테마는 **기본값으로 유지**된다 (하위 호환). DESIGN.md 가 배경을 끄도록 명시한 경우에만 자동 주입을 생략한다. 즉 design/0015(사람 의도 우선)가 design/0010(기본 테마)보다 우선하되, 사람이 아무 말도 하지 않으면 0010 의 기본 동작이 그대로 간다.

## 대안 검토

| 대안 | 설명 | 채택하지 않은 이유 |
|---|---|---|
| 산문 톤에서 금지 의도 추출 | DESIGN.md "톤 & 방향" 산문을 키워드/LLM 으로 해석해 배경을 끔 | 추출 신뢰성이 낮고 매 export 마다 재해석 필요. design/0015 의 "전역 시스템은 결정론 파싱" 원칙과 충돌 |
| 기본 자동 주입 전면 제거 | 타이틀/클로징 배경 주입 자체를 없앰 | 모든 기존·신규 프로젝트의 기본 외형을 바꾸는 파괴적 변경. 그라데이션을 원하는 사용자의 선택지를 뺏음 |
| 프롬프트만 수정 | 타이틀/클로징 프롬프트에서 "배경 자동 삽입" 문구만 제거 | export 의 타입 게이트가 살아 있어 단독으로는 무효 — JSON 이 깨끗해도 export 가 덮어씀 |
| 배경 자산을 톤 중립 PNG 로 교체 | 그라데이션 자산을 차분한 단색 계열로 바꿈 | 모든 프로젝트의 기본 테마를 바꾸는 부작용. 프로젝트별 제어 불가 |
| **DESIGN.md 결정론 키 + export 게이트** | 배경 정책을 파싱 가능한 키로 승격 | **채택** — 결정론적이고, 프로젝트별 제어 가능하며, 하위 호환 유지 |

## Consequences

### Positive

- DESIGN.md 의 디자인 의도가 슬라이드 본문뿐 아니라 배경 선택까지 일관되게 지배한다 (design/0015 원칙 완성).
- 배경 정책이 결정론적으로 파싱돼 매 export 마다 재해석할 필요가 없다.
- 기본값이 그라데이션 유지라 기존·신규 프로젝트 외형은 바뀌지 않는다.
- HTML·PPTX 두 경로가 동일 정책을 따라 미리보기와 최종 산출물이 일치한다.

### Negative / Risks

- DESIGN.md 를 편집하지 않은 신규 프로젝트는 여전히 기본 그라데이션 배경이 나간다 — "그라데이션을 원치 않으면 명시적으로 꺼야 한다"는 점을 사용자가 알아야 한다.
- export 경로가 배경 정책이라는 새 입력을 받게 돼, 명시 배경 우선순위(임포트 라운드트립 보존)와 합성되는 방식을 신중히 유지해야 한다. HTML(이미지 src 우선)과 PPTX(배경 바이트 우선)의 precedence 가 비대칭이라 두 경로를 같은 규칙으로 단순화하면 기존 동작이 깨질 수 있다.
- lint 는 주입된 배경을 보지 못한다(인메모리). 금지 그라데이션이 주입되는 위반을 검출하려면 lint 를 export 산출물 또는 주입 결정 시점으로 확장해야 하며, 이는 본 ADR 범위 밖이다.
