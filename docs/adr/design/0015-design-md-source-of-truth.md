# DESIGN.md — 사람이 편집하는 디자인 의도 단일 소스

Date: 2026-06-15

## Status

Accepted (2026-06-15)

## Context

현재 프레젠테이션의 디자인은 두 갈래로 결정된다.

1. 호출자가 넘기는 테마 입력(다크/라이트) — 디자인 의도로 줄 수 있는 입력이 사실상 이것뿐이다.
2. LLM 이 outline 전체를 보고 자동 생성하는 머신 디자인 요약 — 테마·색 팔레트·폰트·영역 배치 같은 수치화된 스타일 값을 담은 JSON. 이것이 모든 슬라이드 생성 프롬프트에 주입돼 슬라이드 간 일관성을 만든다 (design/0001).

이 구조의 한계:

- **추상 요청을 받을 곳이 없다.** "차분한 파스텔 톤으로", "기업 임원 대상이니 여백을 넉넉히" 같은 사람의 디자인 의도를 생성 *전에* 반영할 통로가 없다. 사후에 부분 수정 경로(modify/0003)로 슬라이드를 하나씩 고치는 수밖에 없어 반복 비용이 크다.
- **페이지별 특별 요청을 담을 구조가 없다.** "3번 슬라이드는 좌우 비교 레이아웃으로", "마지막 장은 CTA 강조" 같은 슬라이드 단위 지시를 기록·전달할 자리가 없다.
- **머신 디자인 요약은 사람이 편집하기 부적합하다.** 픽셀 좌표와 색 배열로 된 머신 포맷이라, 사용자가 직접 톤을 조정하려면 내부 스키마를 알아야 한다.

요컨대 "디자인 디테일에 대한 추상 요청"이 좌표·스타일을 가진 디자인 스펙과 한 덩어리로 묶여 있어, 사람이 의도만 따로 관리할 방법이 없다.

## Decision Drivers

- 사람이 직접 읽고 편집할 수 있어야 한다 (머신 포맷이 아니라 문서).
- 추상 디자인 의도를 슬라이드 생성 *전에* 반영할 수 있어야 한다.
- 디자인 의도를 한 곳에서 관리해야 한다 (슬라이드마다 흩어지지 않게).
- 슬라이드 간 전역 일관성은 그대로 유지해야 한다.
- 수치화된 스타일 값은 결정론적으로 파싱돼 매 생성마다 재해석되지 않아야 한다.

## Decision

프레젠테이션마다 **`DESIGN.md`** 를 도입한다. 사람이 읽고 편집하는 마크다운 한 장으로, 디자인 의도의 **단일 소스(source of truth)** 가 되며 기존 머신 디자인 요약을 **대체**한다.

### DESIGN.md 의 구성 (3개 영역)

1. **전역 디자인 시스템** — 기존 머신 요약이 담던 수치화된 스타일 값(테마·색 팔레트·폰트·영역 배치)을 사람이 읽고 고칠 수 있는 마크다운으로 표현한다. 머신용 JSON 대신 사람용 문서가 정본이 된다.
2. **전역 톤 & 방향** — 색감·격식·청중·여백 등 수치로 떨어지지 않는 추상 의도를 산문으로 기록한다.
3. **페이지별 특별 요청** — 슬라이드 단위 지시를 적는다.

### 문서 포맷 — 구조화된 마크다운

자유 산문이 아니라 **고정 섹션 헤더 + 단순 key/value·bullet 규칙**을 쓴다. 이유:

- 전역 디자인 시스템의 수치값을 매 생성마다 LLM 으로 재해석하지 않고 **결정론적으로 파싱**할 수 있다. 톤·페이지 요청처럼 산문이 자연스러운 부분만 자유 서술로 두고 그대로 프롬프트에 넘긴다.
- 섹션 헤더가 고정이라 파서가 견고하고, 사람도 어디에 무엇을 적을지 명확하다.

파서는 알려진 섹션만 읽고 모르는 키·섹션은 무시(폴백)해, 사용자가 자유 편집해도 깨지지 않게 한다.

### 생성·편집 흐름

- 도구가 outline 을 기반으로 `DESIGN.md` **초안을 자동 생성**한다 (오늘 머신 요약을 LLM 으로 만들던 자리를 대체).
- 사용자가 초안을 열어 추상 요청·페이지별 요청을 채워 넣고 편집한다.
- 디자인 스펙 생성 시 `DESIGN.md` 를 프롬프트에 주입한다 — 전역 영역은 모든 슬라이드에, 페이지별 요청은 해당 슬라이드 생성 프롬프트에만.

`DESIGN.md` 가 없으면(기존 프로젝트·임포트 프로젝트) 생성 시점에 초안을 자동으로 만들어 하위 호환을 유지한다.

### 페이지 ↔ 슬라이드 연결 키

페이지별 요청은 **"번호 + 제목"** 으로 슬라이드와 연결한다 (예: `3. 아키텍처 개요`).

- 1-based 슬라이드 번호로 1차 매칭한다.
- 슬라이드 재배치로 번호가 밀리면 제목으로 보정 매칭한다.
- 둘 다 실패하면 해당 요청은 무시하고 경고를 남긴다 (생성을 막지 않는다).

## 대안 검토

| 대안 | 설명 | 채택하지 않은 이유 |
|---|---|---|
| 머신 디자인 요약 유지 + 필드 추가 | 기존 JSON 에 톤/페이지 요청 필드 추가 | 머신 포맷이라 사람이 편집하기 어렵고, 추상 의도를 산문으로 담기 부적합 |
| 페이지 요청을 outline 에 인라인 | 각 슬라이드 outline 에 디자인 지시 필드 | 디자인 의도가 다시 슬라이드 단위로 흩어져 "한 곳에서 관리" 목표에 역행. 전역 톤을 둘 곳도 없음 |
| 사후 부분 수정만 | 생성 후 슬라이드별 수정 (현행) | 생성 전 의도 반영 불가, 슬라이드마다 반복, 전역 일관성 통제 불가 |
| **`DESIGN.md` 단일 소스** | 사람이 편집하는 마크다운이 정본, 머신 요약 대체 | **채택** — 추상 의도와 페이지 요청을 한 곳에서 관리, 스펙(좌표)과 분리 |

## Consequences

### Positive

- 디자인 의도(추상)와 디자인 스펙(좌표·스타일)이 분리돼, 사용자가 의도만 따로 관리·편집한다.
- 추상 요청과 페이지별 요청을 **생성 전에** 반영 → 사후 부분 수정 반복 호출 감소.
- 전역 영역이 모든 슬라이드에 공통 주입되므로 슬라이드 간 일관성은 그대로 유지된다.
- 사람이 읽는 단일 마크다운이라 리뷰·버전 관리(diff)가 쉽다.

### Negative / Risks

- 마크다운 ↔ 생성기가 쓰는 구조화된 값 사이의 파싱/직렬화 계층이 필요하다. 사람이 자유 편집한 마크다운이 깨질 수 있어 견고한 파서와 폴백이 요구된다.
- 머신 요약을 쓰던 기존 프로젝트는 마이그레이션(초안 자동 생성)이 필요하다.
- 페이지 키가 "번호+제목"이라, 번호가 밀리고 제목까지 바뀐 경우 매칭이 끊길 수 있다 (무시+경고로 처리).

### 검증으로 확인된 사항

- 전역 디자인 시스템은 머신 요약 dict ↔ DESIGN.md 사이를 손실 없이 round-trip 한다 (전 키 동일성 확인).
- 파서 견고성: 빈 문서, 모르는 키·섹션, 숫자가 아닌 값, 한/영 섹션 헤더 혼용, 초안의 placeholder 주석 — 모두 죽지 않고 가능한 부분만 채운다.
- 페이지 매칭: 번호 1차 → 제목 보정(공백·문장부호·대소문자 무시) → 무매칭 시 None. 번호가 밀려도 제목으로 보정됨을 확인.
- 디자인 의도 주입: 전역 톤은 모든 슬라이드에, 페이지별 요청은 매칭 슬라이드에만 프롬프트로 들어간다. 기존 DESIGN.md 가 있으면 초안 재생성 LLM 호출을 건너뛴다.
- 하위 호환: DESIGN.md 부재 시 머신 요약(JSON) 폴백으로 로드되어 기존 소비 경로(생성·수정·리뷰·QA·슬라이드·PPTX)가 무변경으로 동작한다.
- DESIGN.md 와 머신 요약이 **둘 다 없는** 경로에서도 슬라이드 생성 프롬프트는 영역 밴드를 받는다. 전역 디자인 시스템을 읽으라는 지시가 모든 슬라이드에 공통 주입되므로, 의도가 아직 없는 상태에서도 같은 기본 밴드를 실어 지시가 항상 충족되게 한다 — 슬라이드가 각자 임의의 y축 밴드를 만들어 덱 일관성이 깨지는 것을 막고, 나중에 의도가 추가돼도 밴드가 바뀌지 않는다.
