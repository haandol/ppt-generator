# 슬라이드 아웃라인 생성

Date: 2026-02-11

## Status

Accepted (2026-09-08)

## Context

프레젠테이션 생성의 첫 단계는 주제와 발표 조건을 슬라이드 단위의 구조화된
계획으로 바꾸는 일이다. 이 결과는 이후 디자인 생성과 편집의 공통 입력이므로,
클라이언트가 생성한 필드가 검증 과정이나 후처리에서 유실되지 않아야 한다.

아웃라인은 콘텐츠의 주제와 핵심 요점뿐 아니라 슬라이드 유형, 사용할 시각 구조,
요소 수와 관계를 설명하는 레이아웃 방향, 발표자 노트를 함께 소유한다. 색상,
폰트, 정확한 좌표와 크기는 디자인 단계의 책임으로 남긴다.

## Decision Drivers

- 생성 계약과 수신 검증 계약이 달라 생기는 데이터 유실을 방지해야 한다.
- 사용자가 지정하지 않은 무해한 발표 조건 때문에 생성이 중단되지 않아야 한다.
- 발표 형식은 목적에 따라 달라질 수 있어야 하며 특정 목차 구조를 모든 덱에 강제하지 않아야 한다.
- 근거가 있는 사실과 모델이 추론한 가정을 후속 검토에서 구분할 수 있어야 한다.
- 클라이언트가 재전송한 저장 결과도 동일한 계약으로 검증할 수 있어야 한다.

## Decision

아웃라인 생성은 준비와 수신의 두 단계로 나눈다. 준비 단계는 프롬프트와 단일
응답 스키마를 반환하고, 수신 단계는 같은 모델로 전체 응답을 엄격하게 검증한 뒤
저장한다. 선언되지 않은 필드는 거부한다.

각 슬라이드는 제목, 콘텐츠 요약, 컴포넌트 힌트, 슬라이드 유형, 레이아웃 계획,
발표자 노트, 근거 참조 목록과 가정 목록을 포함한다. 근거 참조와 가정은 빈 목록일 수
있지만 필드는 생략할 수 없다. 수치, KPI, 외부 사실처럼 사용자 입력만으로 확정할 수
없는 주장을 추가할 때는 근거 참조를 제공하거나 가정으로 표시한다. 슬라이드 인덱스는
저장 결과를 다시 수신할 수 있도록 허용하되 서버가 최종 순서에 따라 정규화한다.

컴포넌트 힌트는 정식 힌트 집합 또는 `custom`만 허용한다. `custom`은 정식 힌트로
표현하기 어려운 구조를 레이아웃 계획에서 자연어로 설명한다.

슬라이드 수를 명시하면 4장부터 20장까지 허용한다. 생략하면 발표 시간과 콘텐츠
복잡도에서 4장부터 20장 사이로 추론한다. 첫 슬라이드는 title, 두 번째 슬라이드는
agenda, 마지막 슬라이드는 closing이어야 하며 그 사이에 최소 한 개의 content
슬라이드를 둔다. agenda 항목은 모든 슬라이드를 나열하지 않고 본문의 주요 구간을
요약한다.

목적, 발표 시간, 청중 유형과 발표자 정보가 요청 문맥에 없으면 클라이언트는 안전한
기본값을 사용하거나 문맥에서 추론하고 결과에 가정을 알린다. 이 값들을 얻기 위한
사전 질문은 사용자의 요청 경계를 바꾸는 경우에만 필요하다. 발표자 정보가 없으면
가짜 이름·직책·소속을 만들지 않는다.

사용자가 완성된 덱 생성을 요청했다면 그 요청은 아웃라인 다음 단계까지 진행할 권한을
포함한다. 아웃라인만 요청했거나 슬라이드 수·구성 확인을 명시적으로 요구한 경우에만
아웃라인에서 멈춰 확인한다.

## Alternatives Considered

| 대안 | 판단 |
|------|------|
| 준비 단계는 느슨한 JSON 예시만 제공하고 수신 단계에서 필요한 필드만 추출 | 계약 불일치와 조용한 필드 유실을 만들기 때문에 제외 |
| 누락된 발표 조건을 매번 질문 | 정확하지만 무해한 기본값에도 흐름이 중단되고 end-to-end 요청의 자율성이 사라져 제외 |
| Title·Agenda·Closing을 선택 사항으로 둠 | 형식 자유도는 높지만 사용자가 요구한 기본 발표 구조를 보장하지 못해 제외 |
| 준비와 수신이 하나의 엄격한 모델을 공유 | 계약 드리프트를 즉시 실패로 드러내고 필드 보존을 보장하므로 채택 |

## Consequences

- 클라이언트는 반환된 응답 스키마의 모든 필수 필드를 생성해야 한다.
- 잘못된 형식이나 부분 응답은 저장 전에 명시적으로 거부된다.
- 사용자가 지정하지 않은 무해한 조건은 가정으로 보완되어 불필요한 질문이 줄어든다.
- 모든 덱은 Title → Agenda → 최소 1개 Body → Closing 구조를 보장한다.
- 후속 덱 리뷰가 근거 없는 주장과 명시된 가정을 구분할 수 있다.
- 아웃라인 계약 변경은 준비 응답과 수신 검증에 동시에 반영된다.
