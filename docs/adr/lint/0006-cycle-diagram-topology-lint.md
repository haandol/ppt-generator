# 순환 다이어그램 위상 일관성 lint — 선언 기반 사이클 마킹

Date: 2026-06-15

## Status

Accepted

## Context

순환(cycle) 구조 다이어그램 — ReAct 루프(Think→Act→Observe→Think), 피드백 루프 등 — 에서 LLM 이 화살표의 의미적 방향을 반대로 생성하는 결함이 관찰됐다. 노드 좌표와 연결관계는 맞지만 일부 화살표의 화살촉이 흐름과 반대 노드를 가리켜, 순환이 한 방향으로 닫히지 않는다(예: 한 노드에 화살표 2개가 유입되고 다른 노드는 유출만 있음).

기존 화살표 lint(arrow-endpoint-attachment, lint/0004)는 **끝점이 어떤 박스 변에 닿는가(좌표 부착)** 만 검사하고, **어느 노드 → 어느 노드(방향)** 는 보지 않는다. 방향 오류는 좌표상으로는 완벽히 유효해(양 끝이 박스에 닿음) 이 lint 를 통과한다.

근본적으로, lint 가 "올바른 방향"을 절대적으로 판정하는 것은 불가능하다. Think/Act/Observe 라벨의 의미나 ReAct 루프의 올바른 회전방향은 도메인 지식이며 코드에 ground-truth 가 없다. 좌표만 보는 lint 로는 Observe→Act 와 Act→Observe 를 구분할 수 없다.

다만 절대 방향이 아니라 **위상 일관성** — "순환 다이어그램이라면 각 노드의 유입/유출 차수가 1이고 전체가 하나의 방향성 사이클을 이루는가" — 는 좌표·연결만으로 검증 가능하고, 이번 결함을 정확히 잡는다(유입 2/유출 0 인 노드가 생기면 사이클이 깨진 것).

문제는 **"이 다이어그램이 순환인가"를 어떻게 아는가** 다. lint 가 좌표·근접만으로 사이클 여부를 추측하면, 좌→우 파이프라인의 우연한 근접이나 fan-out/fan-in bus 패턴을 사이클로 오인해 false positive 를 양산한다.

## Decision Drivers

- 방향 오류를 생성 단계에서 자동·결정론적으로 검출하고 싶다 (visual_qa 비전 호출 전에).
- lint 는 다이어그램의 의미를 모르므로 "올바른 방향"이 아닌 검증 가능한 속성만 봐야 한다.
- 사이클 여부를 좌표로 추측하면 false positive 가 크다 — 추측을 없애야 한다.
- 기존 lint 의 일관된 성격(감지만, 비차단 warning, 자동교정 안 함)을 따른다.

## Decision

**순환 여부를 lint 가 추측하지 않는다. 디자인 스펙이 "이 묶음은 순환 다이어그램"이라고 명시 선언하고, lint 는 그 선언된 영역에 한해서만 위상 일관성을 warning 으로 검증한다.**

- 디자인 스펙의 의미 트리(레이아웃 노드)에서 한 묶음을 **순환 다이어그램으로 마킹**한다. 마킹 방법(전용 필드 vs 관례 role 라벨)과 노드↔화살표 연결을 무엇으로 판정할지는 design 카테고리의 결정(design/0017)에 위임하며, 본 lint 는 그 마킹과 연결 정보를 입력으로 받는다.
- 마킹된 사이클 영역에서 lint 는 다음만 검사한다: 영역에 속한 노드들이 화살표로 연결될 때 **각 노드의 유입 차수와 유출 차수가 모두 1이고, 전체가 단일 방향성 사이클을 이루는가**. 위반(차수 불균형, 사이클 미형성)이면 warning.
- **"올바른 방향(Think→Act 가 옳다)"은 검증하지 않는다** — ground-truth 가 없기 때문. 시계/반시계 어느 방향이든 단일 사이클로 닫혀 있으면 통과한다. 즉 "사이클이 위상적으로 깨졌다"만 넛지하고, 어느 화살표를 뒤집어야 정답인지는 말하지 않는다.
- severity 는 **warning** — 생성/수정을 차단하지 않고 결과에 노출만 한다. 자동 교정은 하지 않는다 (lint/0003·0004 의 일관된 설계 철학).

## 대안 검토

| 대안 | 설명 | 채택하지 않은 이유 |
|---|---|---|
| 절대 방향 검증 lint | 라벨 의미로 올바른 흐름을 판정 | 코드에 도메인 ground-truth 없음 — 구현 불가 |
| 좌표 휴리스틱으로 사이클 자동 감지 | 노드 근접·연결만으로 "사이클 다이어그램"을 추론해 검사 | 파이프라인 우연 근접·fan-out bus 를 사이클로 오인 → false positive 양산 |
| 검증 없이 프롬프트만 강화 | design 프롬프트에 순환 방향 규칙·예시만 추가 | LLM 준수에 100% 의존 — 미준수 시 안전망 전무 |
| 라인마다 source/target 의미 필드 추가 | 모든 화살표에 출발/도착 노드 명시 | 가장 견고하나 schema·export·parser·다수 lint 에 파급 — 과도. 사이클 마킹+위상 검증으로 이번 결함은 충분히 커버 |
| **선언 기반 사이클 마킹 + 위상 일관성 lint** | 스펙이 사이클임을 선언, lint 는 그 영역만 위상 검증 | **채택** — 추측 제거로 false positive 차단, 가벼움, 의미 불필요 |

## Consequences

### Positive

- 방향 오류로 깨진 순환을 좌표 기반으로 결정론적 검출 — 생성 단계에서 넛지, visual_qa 비전 호출 불필요.
- 사이클 여부를 추측하지 않으므로 false positive 위험이 구조적으로 낮다 (선언된 영역만 검사).
- lint 가 의미를 알 필요가 없다 — "위상 일관성"이라는 검증 가능한 속성만 본다.
- warning 비차단이라 의도적 예외(다중 유입 허브 등)도 무시 가능.

### Negative / Risks

- 디자인 스펙에 사이클 마킹이 없으면 검사 자체가 동작하지 않는다 — LLM 이 마킹을 누락하면 안전망이 비활성. 이를 줄이려면 design 프롬프트가 순환 구조에 마킹을 붙이도록 유도해야 한다 (design/0017 의존).
- 노드↔화살표 연결 판정이 좌표 근접에 기댈 경우, 한 끝점이 두 박스 코너에 동시 근접하면 차수 집계가 흔들릴 수 있다. 연결 판정 방식은 design/0017 에서 정한다.
- 차수 위반을 잡아도 "어느 화살표가 틀렸는지"는 알려주지 못한다 (의미를 모르므로) — 사용자/LLM 이 판단해 수정.

### 검증으로 확인된 사항

- 올바른 단일 순환(Think→Act→Observe→Think)은 위반 0건으로 통과한다. 방향을 의도적으로 깨뜨린 케이스(한 노드 유입 2/유출 0)는 정확히 warning 으로 검출됐다 — 깨진 노드의 차수를 메시지에 노출한다.
- 마킹이 없는 묶음·design_doc 부재·사이클 노드를 잇는 화살표 없음·노드 2개 미만은 모두 검사 제외(보수적)로 동작 — false positive 없음.
- 실제 데크(이번 세션의 ReAct 슬라이드)에 적용해, 사람이 처음 눈으로 발견했던 "왼쪽 화살표 반대" 결함을 동일 배치에서 좌표만으로 재검출함을 확인했다.
