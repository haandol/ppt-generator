# 디자인 스펙 품질 게이트

Date: 2026-04-27

## Status

Accepted (2026-08-29)

## Context

클라이언트 모델이 생성하는 디자인 스펙에는 두 종류의 문제가 섞여 있다.

- 스키마 위반, 필수 연결 누락, 허용되지 않은 값처럼 후속 파이프라인이 의미를
  안전하게 해석할 수 없는 계약 위반
- 작은 글자, 비대칭 간격, 얕은 대각선처럼 결함일 가능성은 있지만 사용자의 유효한
  디자인 의도일 수도 있는 품질 위험

두 종류를 모두 입력 거부로 처리하면 데이터 무결성은 높아지지만 모델이 선택할 수 있는
유효한 표현 공간이 불필요하게 줄어든다. 반대로 모든 문제를 경고로만 처리하면 필수 계약이
깨진 스펙이 저장·렌더 단계까지 흘러갈 수 있다.

프롬프트도 같은 구분이 필요하다. 최종 산출물이 지켜야 하는 계약과 일반적인 디자인
권고를 모두 절대 명령으로 표현하면, 모델은 렌더 가능한 다양한 해법보다 특정 레이아웃
레시피를 반복하게 된다. 품질 게이트는 계약 보존과 모델 자율성을 동시에 지켜야 한다.

## Decision Drivers

- 필수 필드, 허용 값, 참조 관계와 같은 데이터 계약은 저장 전에 반드시 보장되어야 한다.
- 유효한 디자인 의도를 휴리스틱 임계값만으로 거부해서는 안 된다.
- HTML과 PPTX가 같은 디자인 의미를 재현할 수 있는 최종 스펙 정합성이 중요하며,
  모델의 내부 사고 순서 자체는 계약이 아니다.
- 품질 경고는 사용자 동의 없는 재생성이나 Visual QA 실행 권한을 부여하지 않는다.
- 임포트 결과와 생성 결과는 서로 다른 전제를 가지므로 동일한 품질 규칙을 강제하면
  오탐이 실제 결함을 가릴 수 있다.

## Decision

디자인 스펙 품질 게이트를 다음 세 수준으로 분리한다.

### 1. 계약 검증 — 위반 시 거부

후속 단계가 스펙의 의미를 안전하게 해석할 수 없는 경우에만 입력을 거부한다.

- JSON과 응답 스키마를 해석할 수 있어야 한다.
- 필수 필드와 허용 값 집합을 만족해야 한다.
- 식별자 유일성, 참조 대상 존재, 부모·자식 관계와 같은 구조적 불변식을 만족해야 한다.
- prepare 단계에서 고정한 프로젝트, 슬라이드, 스키마와 revision 문맥이 ingest 요청과
  일치해야 한다.
- 값의 의미가 하나로 정의된 필드는 그 단위와 의미를 따라야 한다.

계약 검증은 표현 방식의 선호를 강제하는 수단으로 사용하지 않는다.

### 2. 디자인 lint — 감지하고 보고하되 수정하지 않음

렌더링 품질을 떨어뜨릴 가능성이 있지만 유효한 의도일 수도 있는 항목은 lint로 분류한다.
lint는 위반 위치, 규칙과 심각도를 보고하며 디자인 스펙을 직접 변경하지 않는다.

- 글자 크기, 간격, 정렬, 밀도, 대비와 같은 품질 기준
- 겹침, 캔버스 이탈, 텍스트 넘침처럼 실제 결함일 가능성이 높은 기하·렌더 위험
- 생성 모델이 필드 의미를 혼동했을 가능성은 있지만 유효한 표현과 구별할 수 없는 패턴

예를 들어 line의 두 축 변화량은 끝점 차이를 나타내므로 한 축 변화량이 작아도 유효한
얕은 대각선일 수 있다. 작은 축 변화량을 선 두께로 잘못 사용한 것으로 의심할 수는 있지만,
고정 임계값만으로 해당 line을 거부하지 않는다. 선 두께는 별도 필드라는 계약을
프롬프트와 스키마 설명에 명시하고, 실제 부착·기하 문제는 lint 또는 시각 검증으로
판단한다.

### 3. 생성 지침 — 권고와 예시

디자인 스타일, 반복 요소의 균형, 권장 좌표, 레이아웃 레시피와 예시는 모델이 더 나은
초안을 만들도록 돕는 지침이다. 이 지침은 다음 원칙을 따른다.

- `MUST`, `REQUIRED`, `NEVER` 같은 절대 표현은 계약 검증 대상에만 사용한다.
- 유효한 대안이 있는 디자인 휴리스틱은 권고로 표현한다.
- 예시는 가능한 해법을 보여주며 유일한 정답으로 취급하지 않는다.
- 모델은 최종 응답이 계층·참조 계약을 만족하는 한 생성 과정에서 앞선 선택을 재검토할
  수 있다. JSON 필드의 최종 구조와 필수 관계는 계약이지만 내부 사고 순서는 계약이 아니다.

### 비개입과 사용자 권한

의미 변화가 없는 기계적 정리만 자동 적용할 수 있다. 위치, 크기, 글꼴, 색상, 텍스트,
요소 수와 같은 디자인 의미는 lint가 자동 변경하지 않는다.

lint 경고는 사용자에게 보고하거나 이미 허용된 읽기 전용 검사를 수행할 근거가 될 수
있지만, 사용자 동의 없이 Visual QA 수정 루프나 전체 슬라이드 재생성을 시작하는 권한은
아니다. 수정이 필요한 경우 사용자가 승인한 편집 범위 안에서 수행한다.

### 입력 출처별 프로필

프로필을 지정하지 않은 생성 결과에는 전체 생성용 lint 정책을 적용한다.

임포트 결과에는 원본 충실도와 무관하게 문제가 되는 렌더 안전 규칙만 명시적으로
적용한다. 생성 전용 계층·스타일 규칙은 임포트 프로필에 자동 포함하지 않는다. 알 수 없는
프로필은 전체 규칙으로 조용히 대체하지 않고 오류로 보고한다.

### 계약 테스트

테스트는 다음 경계를 고정한다.

- 계약 검증 대상은 잘못된 입력을 거부한다.
- 유효한 대안이 존재하는 휴리스틱은 입력 거부가 아니라 lint 또는 권고로 남는다.
- lint 실행 전후의 디자인 스펙은 의미적으로 동일하다.
- 프롬프트의 절대 명령은 계약 검증 대상과 대응한다.
- 사용자 동의가 필요한 품질 작업은 다른 스킬이나 문서에서도 같은 권한 규칙을 따른다.

## 대안 검토

| 대안 | 판단 |
|---|---|
| 모든 품질 규칙을 스키마 검증으로 강제 | 결정론적이지만 유효한 디자인 표현까지 거부하고 모델 자율성을 과도하게 제한하므로 제외 |
| 프롬프트만으로 모든 결함을 예방 | 생성 편차와 복잡한 기하 관계를 완전히 통제할 수 없고 계약 위반이 저장 단계까지 도달할 수 있어 제외 |
| 모든 문제를 lint 경고로만 처리 | 필수 필드와 참조 무결성까지 깨진 스펙을 허용하므로 제외 |
| 계약 검증·비차단 lint·생성 권고를 분리 | 필수 계약을 보존하면서 유효한 표현 공간과 사용자 수정 권한을 유지하므로 채택 |

## Consequences

### Positive

- 필수 데이터 계약은 ingest 경계에서 결정론적으로 보장된다.
- 휴리스틱 오탐 때문에 유효한 디자인이 거부되는 일을 줄인다.
- 모델은 고정 템플릿이 아닌 다양한 레이아웃과 시각 표현을 선택할 수 있다.
- lint, Visual QA와 사용자 편집의 권한 경계가 명확해진다.
- 프롬프트를 줄이거나 예시를 교체해도 최종 계약은 스키마와 검증에 남는다.

### Negative / Risks

- 일부 품질 경고는 사용자가 수정하지 않으면 결과물에 남을 수 있다.
- 계약 검증과 lint의 경계가 모호한 새 규칙은 사람이 유효한 대안 존재 여부를 판단해야 한다.
- 권고 표현을 약화하면 생성 품질이 흔들릴 수 있으므로 대표 시나리오 회귀 테스트와
  시각 검증이 필요하다.

## Acceptance Criteria

- 필수 필드, 허용 값과 참조 무결성 위반은 ingest 전에 거부된다.
- 얕은 대각선처럼 유효한 해석이 가능한 기하는 휴리스틱 임계값만으로 거부되지 않는다.
- 디자인 lint는 입력 스펙을 자동 수정하지 않는다.
- 프롬프트는 계약과 디자인 권고를 구분하며 내부 사고 순서를 강제하지 않는다.
- lint 경고만으로 사용자 동의 없는 Visual QA 수정이나 전체 슬라이드 재생성을 실행하지 않는다.
- 생성용 기본 프로필과 임포트용 허용 목록 프로필의 기존 동작은 유지된다.
