# 점진적 구체화 파이프라인 설계 (Progressive Refinement Pipeline)

Date: 2026-02-11

## Status

Accepted (2026-02-11)

## Context

프레젠테이션 자동 생성 시스템의 파이프라인을 설계할 때, 두 가지 핵심 과제가 있다:

1. **LLM의 한계 관리**: 하나의 LLM 호출로 "주제 → 완성된 PPTX"를 한 번에 처리하면, 구조·내용·디자인을 동시에 고려해야 하므로 품질이 떨어진다. 각 단계를 분리하면 LLM이 한 가지에 집중할 수 있다.
2. **디자인 자유도 최대화**: 최종 산출물은 편집 가능한 PPTX여야 하지만, python-pptx로 직접 생성하면 고정 플레이스홀더와 제한된 스타일링으로 디자인 자유도가 크게 떨어진다.

## Decision

**추상에서 구체로의 점진적 구체화(Progressive Refinement)** 원칙으로 파이프라인을 설계한다. 각 단계는 이전 단계의 출력을 더 구체적인 형태로 변환하며, 디자인 자유도를 최대한 보존한다.

```
텍스트 (가장 추상적)       — 사용자의 주제 입력
  → 아웃라인 (구조화)      — 슬라이드 구성·요점·레이아웃을 JSON으로 정리
    → 디자인 의도          — 덱 전체의 테마·톤·슬라이드별 특수 지시
      → 디자인 스펙         — 구조화된 JSON으로 정밀한 레이아웃 설계
        ├→ HTML 슬라이드    — 결정론적 변환, 브라우저 미리보기용
        └→ PPTX             — 결정론적 변환, 편집 가능한 포맷
```

### 각 단계의 설계 의도

| 단계 | 추상화 수준 | 설계 의도 |
|------|-------------|-----------|
| **텍스트** (사용자 입력) | 가장 추상적 | 사용자는 주제만 제공. 구조화 부담 없음 |
| **아웃라인** | 구조화 | 슬라이드의 뼈대와 발표 narrative 초안을 JSON으로 정리. 제목, 내용 요약, 배치 방향, 요소 수와 관계를 결정 |
| **디자인 의도** | 덱 단위 방향 | 사람이 편집할 수 있는 테마·톤·슬라이드별 특수 지시를 확정 |
| **디자인 스펙** | 정밀한 레이아웃 설계 | 클라이언트 모델이 각 요소의 좌표·크기·서식을 설계. 단일 소스에서 HTML과 PPTX를 결정론적으로 생성 |
| **HTML 슬라이드** (F3) | 브라우저 미리보기 | PptxSlideSpec → position:absolute HTML로 결정론적 변환 (LLM 미사용) |
| **PPTX** (F5) | 편집 가능한 최종물 | SlideBuilder가 PptxSlideSpec에서 직접 PPTX 생성 (LLM 미사용) |

### 왜 아웃라인과 디자인 의도를 분리하는가

- **관심사의 분리**: 아웃라인은 무엇을 어떤 순서와 관계로 보여줄지 결정하고,
  디자인 의도는 덱 전체의 시각 언어를 결정한다.
- **단계적 확정**: 사용자가 구조를 먼저 확인한 뒤 디자인 생성으로 넘어갈 수 있다.
- **클라이언트 집중도**: 각 생성 단계가 한 종류의 결정에 집중하므로 계약 경계가 명확하다.

### 왜 디자인 스펙을 중간 표현으로 사용하는가

- **단일 소스**: PptxSlideSpec JSON 하나에서 HTML과 PPTX를 각각 결정론적으로 생성하므로 변환 과정의 정보 손실이 없다.
- **모델 친화성**: 클라이언트 모델은 구조화된 JSON으로 좌표·크기·서식을 설계한다.
- **시각적 확인**: HTML 미리보기로 사용자가 확인 후 PPTX로 변환하는 워크플로를 지원한다.

### 왜 PPTX로 최종 변환하는가

- **실무 편집성**: PPTX는 PowerPoint/한쇼에서 드래그&드롭으로 편집할 수 있다.
- **조직 표준**: 대부분의 비즈니스 환경에서 프레젠테이션의 표준 포맷은 PPTX이다.
- **개별 객체 편집**: 디자인 스펙의 각 요소를 PPTX의 독립적인 객체(텍스트박스, 이미지, 도형)로 변환하여 개별 편집 가능하다.

### Alternatives Considered

1. **LLM → PPTX 직접 생성**: python-pptx 코드를 LLM이 생성하는 방식. 디자인 자유도가 크게 떨어지고, LLM이 python-pptx API를 정확히 호출하는 코드를 생성하기 어려움. 탈락.
2. **단일 단계 생성**: 주제 → 바로 HTML 슬라이드. 구조·내용·디자인을 동시에 고려해야 하므로 품질이 떨어짐. 탈락.
3. **이미지 포함 Markdown 중간 표현**: Markdown은 레이아웃 자유도가 HTML 대비 크게 부족. 탈락.

## Consequences

### 긍정적

- 각 단계가 독립적이므로, 특정 단계만 재실행하거나 중간 결과물을 저장/로드할 수 있다
- LLM이 각 단계에 집중하여 출력 품질이 높아진다
- 사용자가 각 단계 사이에 검토·수정할 수 있다
- 디자인 스펙 중간 표현으로 HTML↔PPTX 간 레이아웃 일치도가 높다

### 부정적

- 단계가 많아 전체 파이프라인 실행 시간이 증가한다
- 여러 prepare/ingest 왕복과 클라이언트 생성 단계 때문에 실행 시간이 늘어날 수 있다
